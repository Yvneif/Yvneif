I'm an Associate Software QA Engineer at Qstrike Innovations, where I run functional, regression, smoke, and UAT testing on production web apps and track everything through Jira and Xray. Somewhere along the way I started building more tooling than test cases — automated checks, visual regression runs, CI gates — because I'd rather catch a break in a build log than in a bug report.

That's also why data engineering is where I'm headed. A pipeline is a system whose failure modes you get to design around, and finding them early is the part of QA I already enjoy — just one layer downstream, before the data reaches anyone.

## 🧪 What I work on

- **Test automation** — Built QA-as-Code Starter, a Playwright + TypeScript suite running across a
  three-browser GitHub Actions matrix (Chromium, Firefox, WebKit), so a regression shows up as a red
  build instead of getting caught two sprints later.
- **Visual regression** — CrossBrowser-Check pixel-diffs the same page across browsers and viewport
  sizes and turns the result into a report a reviewer can act on, not two screenshots they have to
  squint between.
- **Testable architecture** — On ThesisArchive, structured the .NET backend so validation, auth, and
  workflow logic sit in services that unit, integration, and Playwright tests can reach without a
  browser standing in for every check.

## 🎯 How I approach quality

- **Risk first.** Coverage that mirrors how the product is actually used beats coverage that only
  inflates a number.
- **Fail loudly in CI.** A test that no build depends on is documentation, not a safety net.
- **Document the tradeoffs.** Every tool has cases it handles badly, and those belong in the README
  next to the happy path rather than hidden in a wiki nobody reads.
- **Leave a trail.** Review decisions, migrations and release notes are part of the deliverable, not
  cleanup for later.
